# 编写与二次审核

## 要求、例子和事实

模板决定栏目与问题，参考例子帮助理解写法，事实材料提供具体内容。用户提供多份指导文件时一起核对；有矛盾时找清版本和适用范围，只对会实质改变写法的冲突询问。不要把填写示例里的固定次数、阈值或签字流程自动当作正式要求。

在任务记录中保存下表即可，不额外让用户填一次：

| 当前要求 | 必须回答的问题或关系 | 拟放位置 | 来源 | 状态 |
| --- | --- | --- | --- | --- |

按条目目的选择结构。例如需要说明技术覆盖就逐层对应服务、产出与承担方；需要说明交付过程就按阶段写动作、交接和验证；一般报告遵循其模板。方法论与案例应有对应关系，但不强制任何文档都写方法论。

## 框架确认

展示具体写法、事实基础、表格列、配图及必要未知。用户确认后继续正文；直接出稿的明确要求优先。用户更正意见时修改相关框架，不要求重做未变部分。确认记录写明哪一版/哪些部分获认可，不把用户一句局部同意扩展为所有内容审核完成。

## 写作约定

- 方法讲动作、判断依据和产出；案例讲实际怎样做、为何这样选择及结果。只写有根据的业务关系。
- 价值按功能展示、实际使用、测算收益或已实现收益的真实状态表述，不混用批次、场景和项目。
- 图表只放支持具体论点的必要内容，不凑数量。图片看过且有可用版本才插入，图注与处理后的画面一致。
- 必要待填在原位置，例如“承担团队：____”；未确认不等于“无”。可选细节省略，避免庞大补件清单。
- 正文完整，编号和层级服从模板。默认统一纵向；宽矩阵优先调整措辞、列宽及跨页，明确需要横向时再采用。
- 修改稿输出完整连续版本。引用要求以用户或模板为准；内部证据映射保留在工作记录，不用空引用代替说明。

## 二次审核

| 检查 | 实际核对 |
| --- | --- |
| 要求覆盖 | 每个要求在哪段或哪个单元格被回答，关系和理由是否讲清 |
| 来源和事实状态 | 数据、主体、时序、实际/计划、演示/运行、测算/实现是否与来源一致 |
| 混入内容 | 是否移入其他项目、参考例子或未经核对的模型推断 |
| 图文与脱敏 | 图片支持论点、编号正确、敏感字段处理符合确认范围、必要信息仍可读 |
| 缺项 | 是否确为任务所需，是否已有材料可回答，必要未知是否原位标注 |
| 文稿完整 | 模板字段、章节、表格、图注完整，已删除空引用和未执行的编辑说明 |
| 表达 | 删除空泛成效、重复辩解和不必要限定，不能为自然化新增事实 |
| 文件质量 | 可编辑内容可用，图片实际嵌入，中文显示正常，表格与分页可读 |

问题直接修正，修改后检查受影响部分。将“充分回答、必要待填、尚未回答”分别记录；不将待填视为实证完成。主要案例或核心结构改变才返回用户确认。

## 输出

按用户要求提供完整正文或文件。Office 文件使用宿主可用文档工具；生成后优先渲染检查，无法渲染时进行结构检查并如实说明。需要红字时实际设置颜色，不把 HTML 标签写进 Word 正文。

只报告影响使用的限制。没有实际导出成功就不声称已有文件；没有正式提交就不声称提交完成。新稿与项目汇总分开存放，更新事实资料须有对应原材料或明确用户补充。
